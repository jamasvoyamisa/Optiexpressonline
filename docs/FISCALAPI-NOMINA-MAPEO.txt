RESUMEN EJECUTIVO
-----------------
Integración timbrado con FiscalAPI: VIABLE para nómina ordinaria básica.

  Cobertura de datos existentes ........ ~70 % (emisor, receptor, complemento base)
  Cobertura de cálculo v1 .............. ~55 % (falta otros pagos / códigos SAT finos)
  Código de integración PAC .......... 0 % (no hay cliente HTTP ni builder JSON)

  Esfuerzo estimado (sandbox, nómina ordinaria, 1 empresa):
    - Builder JSON + servicio timbrado ........ 1–1.5 semanas
    - Endpoints + UI "Timbrar periodo" ........ 0.5–1 semana
    - Config FiscalAPI (API key, CSD) ......... 0.5 semana
    - Pruebas contador / revisión E 2026 ...... 1 semana
    TOTAL ..................................... 3–4 semanas (sin ampliar motor de cálculo)

================================================================================

4. JSON INTERNO ACTUAL (calculo_nomina.py) vs FISCALAPI
================================================================================

  Percepción ejemplo actual:
    { "clave": "001", "tipo": "percepcion", "concepto": "...",
      "importe_gravado": 8500.00, "importe_exento": 0 }

  Deducción ejemplo actual:
    { "clave": "002", "tipo": "deduccion", "concepto": "ISR (...)",
      "importe": 450.00 }

  Ajuste mínimo para timbrar:
    - Renombrar / duplicar en builder: clave → earning_type_code / deduction_type_code
    - Agregar "code" interno por línea (ej. secuencial "1001", "5001")
    - Crear other_payments desde subsidio_causado cuando > 0
    - Validar revisión E 2026: percepción 038 solo gravada; subsidio máx $628

6. MODOS FISCALAPI
================================================================================

  A) Facturación por VALORES (recomendado para arranque)
     - Enviar RFC, nombres, CSD en cada request (como el ejemplo del SDK)
     - No requiere sincronizar catálogo Person en FiscalAPI
     - Más payload por request

  B) Facturación por REFERENCIAS
     - Crear emisor/receptor/empleado en FiscalAPI (UUIDs)
     - Timbrar con issuer.id / recipient.id
     - Requiere sync al alta/baja de empleados y empresas
     - Mejor a largo plazo para volumen alto

7. BRECHAS DE CÁLCULO (afectan timbrado aunque exista el PAC)
================================================================================

  Estos temas NO los resuelve FiscalAPI; hay que completarlos en Optiexpress
  antes de timbrar recibos reales:

  [ ] Subsidio al empleo en other_payments (dato existe, no se emite)
  [ ] Separar gravado/exento correctamente por tipo de percepción
  [ ] IMSS: clave deducción SAT correcta + desglose por ramo (opcional)
  [ ] INFONAVIT: factor vs monto fijo
  [ ] Horas extra, faltas, incidencias → percepciones/deducciones
  [ ] Nómina extraordinaria (aguinaldo, finiquito) — ejemplos 7–9 en SDK
  [ ] Incapacidades — ejemplo 5 en SDK (CFDI distinto o nodo disability)
  [ ] Validar totales: Comprobante.Total = suma percepciones - deducciones + otros pagos

================================================================================
9. COMPARACIÓN CON FACTURAMA (decisión PAC)
================================================================================

  Optiexpress hoy modela facturama_user/password en empresa_nomina_config.
  FiscalAPI usa API key + tenant (modelo distinto, mismo rol: PAC).

  El builder de JSON/complemento es 90 % igual entre PACs; solo cambia:
    - URL base y autenticación
    - Formato exacto del JSON (FiscalAPI Invoice vs Facturama cfdi JSON)
    - IDs de respuesta y descarga de archivos

  Recomendación: abstraer capa "PacNominaProvider" con implementación FiscalAPI
  primero; Facturama como alternativa si ya tienen contrato.


================================================================================
10. CONCLUSIÓN
================================================================================

  Los modelos empleado_nomina + detalle_nomina_empleado + personal/empresa
  cubren la mayoría de campos del ejemplo "Nómina ordinaria" de FiscalAPI.

  Lo que falta NO es tanto schema de BD como:
    1) Servicio de timbrado + mapper JSON
    2) Otros pagos (subsidio) y códigos internos por concepto
    3) Config PAC y CSD
    4) Completar validaciones y reglas de cálculo para producción

  Distancia hasta timbrado de PRUEBA en sandbox: ~3 semanas dev.
  Distancia hasta nómina de PRODUCCIÓN confiable: + cálculos + contador (+2–3 meses).
